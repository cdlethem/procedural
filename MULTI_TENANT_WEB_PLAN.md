# Multi-tenant web application

## Context

Expand Procedurals into a multi-tenant application where every interactive visitor receives a persistent user record and a private anonymous session before signup. Signup completes that same application user record without changing its ID or moving its saved layers, palettes, explorations, Studio work or other owned rows. Anonymous users receive a small operator-model AI trial and lower configurable capabilities/quotas; their saved data has no automatic expiry. Public signup remains disabled initially, independently of anonymous access; self-host on the current server with a portable cloud boundary and separate private application/public OSS toolkit repositories.

## Confirmed starting point

- `apps/README.md:36-38` and `docs/web-app-architecture.md:52-57` explicitly describe shared trusted-local storage without accounts or ownership.
- `apps/web/next.config.ts:11-12` proxies `/api/*` to Go; harness handlers live independently under `/harness/*`. Neither a page-only gate nor protecting only `/api/*` covers this application.
- `apps/server/server.go:198-347` exposes shared project CRUD, validates inputs, and blocks cross-site fetch metadata on mutations but does not authenticate users.
- `apps/web/lib/harness/store.ts` stores immutable artifacts and mutable candidates/jobs/apply records in shared directories. Artifact content identity is a hash, not proof of authorization.
- `apps/web/lib/harness/core.ts:35-43` derives writable data paths from the repository checkout. `jobs.ts:149-153` starts local detached workers. Both must change for portable multi-instance hosting.
- `tools/harness/run_p5_layer.mjs:124-129` launches Chromium without its sandbox and installs network interception on only the initial page. Public multi-user rendering requires stronger execution isolation, not just login.
- Current deployment inspection found loopback Next/Go/model listeners behind tailnet-only ingress, user services without resource/isolation hardening, and no app credentials required for read-only API access. These observations describe the current deployment, not an approved public boundary.

## Selected architecture

- User selected built-in accounts and a private web application repository. Use maintained Better Auth email/password authentication with email verification, recovery, server-side sessions and TOTP; do not implement password/session cryptography from scratch.
- Create the private application checkout at `/home/colin/dev/procedurals-web` (confirmed absent during planning). Keep the existing `procedural` repository as the MIT public toolkit. Existing published MIT code cannot be made retroactively private; preserve its notices and public history.
- Establish versioned toolkit/build-input artifacts before extracting the app. The private application must build without an adjacent public checkout. Package/API docs, examples and algorithm contracts remain public; authentication, private persistence, UI/server orchestration and deployment belong to the private application.
- Each application user is a personal tenant, including anonymous visitors. Its immutable application user ID is the ownership key; authentication-library subject IDs are replaceable credentials linked to that record, not foreign keys used by saved work. Signup completes the existing user in place; do not migrate content into a newly created application account.
- Consolidate the Go project CRUD into the authenticated Next server and retire Go app deployment after its validation contracts are ported. PostgreSQL owns metadata, queue state and authorization relations. Immutable bytes use one private BlobStore contract: a durable filesystem volume initially, and an implemented S3 adapter for cloud relocation.
- Keep portable document schemas and hashes content-only; put ownership outside document JSON. Scope every object lookup, relationship, download, idempotency record and job publication to the authenticated owner.
- Reuse the vintage-data connection UX, not its global Airflow storage: per-user OpenAI-compatible endpoints/API keys, test-and-load-models before save, no secret readback, explicit model selection and memory-only key drafts. Its UI does not implement native provider OAuth; compatible external gateways can supply that integration without importing Airflow or command execution.

## Further confirmed findings

- `apps/web/components/Studio.tsx` uses one `procedurals-studio-v1` localStorage key; `Explorations.tsx` keeps results in component memory. Identity-bound server persistence and account-switch clearing are required, not merely per-user list filtering.
- `documents.ts` calls the transport origin `owner`; this is not a user. `tools.ts` has only `Caller.origin` and `applyScopes`; the background loop uses a global caller. All require explicit server-resolved principal propagation.
- Artifacts and export IDs are deterministic hashes, private previews currently use public immutable caching, and apply idempotency keys are globally scoped. Tenant isolation must cover the full reference graph.
- `packages/javascript/package.json` names `@procedurals/javascript`, marks it private, and exports only its main entrypoint. App adapters directly import source/example paths; the existing generators consume catalog, validation, docs and package files. Extracting directories alone will not produce an independently buildable private application.
- `vintage-data/.../model_settings.py:41-60,106-144` verifies HTTPS/public endpoints (explicit local exceptions), tests `/models`, bounds results and encrypts keys in Airflow. Its DNS validation and connection resolve separately: the new client must pin a validated address for each request to avoid copying that SSRF gap.
- Better Auth's anonymous plugin creates an anonymous auth user/session, but its documented onLinkAccount flow receives distinct anonymousUser/newUser identities and normally deletes the former. Do not mistake that for stable-ID completion. Keep the stable application user independent of auth subjects and explicitly control completion/verification; do not use a callback that copies content or blindly merges an existing login.
- Session policy is a hard 24-hour maximum for every session, anonymous or registered, without activity-based renewal. Registered users can authenticate again; anonymous users cannot recover the old workspace after their initial access deadline. Anonymous saved records still have no automatic deletion.
- Anonymous policy decisions: enable a small operator-provided AI trial, not visitor-supplied credentials/API tokens; retain anonymous saved data without time-based deletion. Anonymous creation and trial issuance therefore require installation-wide admission/storage budgets as well as per-user limits, since clearing cookies can create another visitor identity.

### 2. Create tenant-owned persistence and retire shared global stores

Use PostgreSQL 17, `pg`, reviewed numbered SQL migrations and ordinary parameterized SQL. Better Auth owns credential/session records in `auth`; the application owns `app.users`. `app.users.id` is a server-generated UUID and the permanent personal-tenant key from the first anonymous visit onward. Store it as canonical UUID text consistently in `app.users.id` and every `owner_id text`/composite FK, with database format validation; it is never an auth subject ID, email, client workspace ID or browser fingerprint.

Fresh database order: `db:provision` creates logins/schemas; reviewed migrations create generated Better Auth tables (including anonymous-plugin fields), then app.users/auth_identities/account_completions, tenant tables/composite FKs, task/admin functions, then FORCE RLS and final grants. Runtime processes refuse readiness at an incompatible migration level. Auth subject deletion must not cascade into application users or their work.
Pass a dedicated `pg.Pool` to Better Auth with `options:"-c search_path=auth,pg_catalog"`; use the same schema selection for generation and reviewed migrations. Provision `auth` first under the migration owner, deny runtime schema/table creation and remove `public`/user-writable schemas from the auth path. Readiness checks schema/migration identity. A decoy same-named table in `public` must neither satisfy readiness nor receive runtime auth queries.

First deliver `db:provision`, `db:migrate`, `test:integration` and the database/blob portion of `verify:stack`, with minimal disposable Compose and ops-image inputs from step 9. Add mail/auth setup in step 3 and worker/browser profiles as their implementations arrive; the final full-stack invocation remains the one specified under Verification. Focused early checks use the real roles/migrations and explicitly report unavailable components, not bypasses or a claim that a partial stack passed the full suite.

**New server boundary:** `apps/web/lib/server/{db,principal,blobs,repositories}.ts`. Mark server-only modules with `server-only` imports. Define:

```ts
type Principal = Readonly<{
  userId: string;
  role: "user" | "admin";
  accountKind: "anonymous" | "registered";
  credential: "session" | "api-token" | "job";
  credentialId: string;
}>;
type TenantTx = { client: PoolClient; ownerId: string };
function withTenant<T>(principal: Principal, fn: (tx: TenantTx) => Promise<T>): Promise<T>;
function requirePrincipal(request: Request): Promise<Principal>;
interface BlobStore {
  put(key: string, body: ReadableStream<Uint8Array>, expected: {bytes:number,sha256:string}): Promise<void>;
  get(key: string, range?: {start:number,endInclusive:number}): Promise<ReadableStream<Uint8Array>>;
  stat(key: string): Promise<{bytes: number} | null>;
  delete(key: string): Promise<void>;
}
interface MaintenanceBlobStore extends BlobStore {
  list(prefix: string, cursor?: string): Promise<{
    entries: {key:string,bytes:number}[];
    nextCursor: string | null;
  }>;
}
```

`Principal` is constructed only by trusted session/token/job resolution. HTTP/tool JSON cannot supply identity, role or credential kind. For browser/token repositories, `withTenant` acquires one pooled connection, begins a transaction, applies `set_config('app.owner_id', userId, true)`, executes the callback, and commits/rolls back before release. No connection-global SET or mutable global principal. Worker repositories instead use the lease-checked functions below; `withTenant` rejects a job principal. `withClaimedTask({taskId,token,epoch},fn)` binds the verified lease in server-only AsyncLocalStorage across worker calls, not in tool arguments or public JSON.

**Database authority and rows:**

- Use distinct migration-owner, auth, app-request, coordinator, render and maintenance database logins. Runtime roles are not table owners, superusers or BYPASSRLS and cannot create roles/schemas/extensions. Auth has no user-content grants. Worker logins have no direct content/vault table grants: only their kind-specific task functions. Request-role SQL remains a trusted server boundary; a caller-writable tenant setting is not protection against compromised server SQL execution.
- Enable/FORCE RLS on tenant-owned tables. App-request policies use identical USING/WITH CHECK predicates `owner_id = nullif(current_setting('app.owner_id', true),'')`; missing context denies reads/writes. Also use explicit owner predicates and composite `(owner_id,id)` FKs. Task functions have separate non-login, non-inheritable definer-owner roles with explicit table-specific RLS policies/grants sufficient for their kind, including cross-owner queue claim. These are deliberate narrow policy exceptions, not runtime BYPASSRLS or universal owner-equality policies that would make claiming impossible. Revoke PUBLIC execution, fix search_path, schema-qualify objects and never grant runtime logins membership in definer roles.
- Freeze the task-function inventory with the task schema: claim/heartbeat/finish/cancel, read inputs/admitted credential version, reserve/record attempts, publish run step/candidate/render result, and kind-specific mail/export/purge/GC operations. Share pure TypeScript document/hash/protocol validators between HTTP and worker paths; SQL owns the minimal lease, relationship, quota and publication invariants. A principal-aware repository dispatches browser/token work to `TenantTx` and job work to the corresponding fixed task function under `withClaimedTask`; it never falls back to request-role SQL for a job. Worker rejection by `withTenant` is intentional, not a second implementation of every validator.
- This deliberately costs a small, versioned SQL task API plus role/lease tests in addition to shared TypeScript validation. SQL enforces task/entity/kind, lease, quota and publication invariants; it does not duplicate document validators or orchestration. An `assert_lease` followed by worker-controlled `SET app.owner_id` would permit unrelated mutations/vault reads within that owner and is not the selected boundary. Review the function inventory once, not an unrestricted generic SQL dispatcher.
- Threat boundary: visitors, model output, submitted code and provider responses are untrusted; web/coordinator/supervisor code is trusted but separately privileged. Coordinator compromise can expose plaintext/ciphertext for valid tasks it can claim, including successive claims. It must not enumerate unrelated vault rows or accept arbitrary owner/version selectors. The vault key is not supplied to renderers, maintenance or the blob store; no vault ciphertext is placed in blob objects. Full web or database/key-store compromise is outside the protection supplied by worker RLS and must not be described as covered.
- `app.users`: immutable `id`, nullable display_name/email until completion, `account_kind:anonymous|registered`, `role:user|admin`, `state:provisioning|active|suspended|deleting`, completed_at, created_at, last_seen_at, policy_version and quota overrides. Anonymous users are active ordinary users, not provisioning/disabled accounts. Only trusted completion/admin methods change kind, role, state or quotas. Registered email/name updates are synchronized from verified library flows; generated anonymous placeholder emails never become public profile data.
- Add immutable anonymous_access_expires_at to app.users for visitor creation, and expose it only as a non-secret UI deadline. It is not an account-deletion timestamp and becomes irrelevant to registered access after legitimate completion; never recompute it from last_seen_at or a new cookie.
- `app.auth_identities`: unique auth_user_id FK to the library user, user_id FK to app.users, `kind:anonymous|registered`, `state:pending|active|retired`, nullable completion_id. `app.account_completions`: UUID, user_id, originating anonymous auth ID, proposed registered auth ID, normalized email, state/reservation/idempotency fields and timestamps. These are server-owned mapping/lifecycle tables, never client-mutable identity fields. Resolve every session/token/job to the stable app user before RLS. Creating a pending credential identity for signup must NOT allocate a second app user.
- Enforce partial unique indexes for one live completion and one pending-or-active registered identity per app user; auth_user_id is globally unique in the mapping table. Persist a creation receipt keyed by server completion ID and the actual library-created subject. Completion uses step 2's common owner/operation-scope/key idempotency contract; never treat a synthetic signup result or email lookup as creation evidence.
- Trusted creation hooks distinguish visitor bootstrap, completion and operator provisioning by server-only intent, not request JSON. Missing/ambiguous identity mapping denies access until reconciled from a recorded creation receipt; do not guess ownership by email.
