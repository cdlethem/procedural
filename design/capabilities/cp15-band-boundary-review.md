## Boundary choices for the subsequent decision

A private scalar callback makes the experiment small; it is not permission to expose host
callbacks in portable descriptors. The lowest-cost candidate public boundary is one retained
noise-band trace using the existing GradientNoise2D01 descriptor, explicit start/heading,
step distance, tolerance, attempted-work budget and seed. As in GradientPath2D, callers place
and draw multiple traces. Noise scale and offset remain separate from drawing units.

This would deliberately specialize the field while removing the acceptance algorithm.
Analytic transfer would show that the algorithm generalizes, but would not establish public
analytic-field support. Do not add a field-expression evaluator or a scalar-raster API just
to make this one prototype's callback serializable. A reverse-communication propose/accept
stepper is possible, but puts more state and loop wiring on every artist; it is not admitted
without an example showing that burden earns its flexibility.

Proposal steering must be explicitly specified, not an unexplained bag of callbacks. Preserve
the inspected nested proposal and rejection-only heading effects in the initial candidate;
separate deliberate RNG/noise divergences from source replay. A final contract should reuse
the established seeded xoshiro stream rather than promote the experiment's xorshift stream.
No public defaults or recommended parameter intervals are justified by two prototype values.

Branch-sensitive numeric decisions require a stronger profile than approximate rendered
coordinate agreement. Reuse LinePool2D's explicit fdlibm/StrictMath policy for elementary
functions if this candidate is admitted. A tiny coordinate difference can change acceptance
and every later step; never apply a blanket output tolerance to hide a different path.

Store accepted vertices only and distinguish attempted, accepted and rejected counts. The
attempt budget bounds work; a separate retained-vertex cap may provide early resource failure,
with no partial path returned. Zero work, zero tolerance, stationary steps, exact-boundary
rejection, finite field queries and error order need explicit contract decisions and analytic
fixtures. This document is a design review in progress, not those frozen semantics.

Root owns admission, contract, fixtures and final native/package review. No catalog, shared
support or implementation status changes until the experiment is reviewed and the boundary
is frozen. Ports and Sol remain paused.

## Root admission after prototype inspection

The three-image decision is positive; see the experiment's decision.md and hashed results.
Admit `path.noise-band-trace-2d` for contract preparation, extracting the proposal/acceptance
traversal from venas#0. The first operation accepts the existing noise descriptor, one start
and heading, private seed, attempts, step distance, field scale/offset, tolerance and retained
vertex cap. Output is one immutable path including its start, accepted vertices and
attempt/accept/reject counts. No drawing, palette, walker placement, callback or analytic
field mode is included. No positional clamp, collision avoidance or closed-contour promise.

Keep the nested half-pi proposal and .1-radian rejected-heading perturbation as named fixed
algorithm policy for this version. These are source-policy constants, not public recommended
values or generic steering controls. Publicly expose tolerance and explicit spatial/work
inputs; do not promote every source literal. Exact numeric domains and ordered failures are
contract work, not remaining architecture questions. Reuse established xoshiro/fdlibm semantics.

This adds a distinct artist capability at a manageable single-trace boundary. Wider tolerance
is a demonstrated structural edit; retained output supports independent styling. For native
acceptance, transfer the same path to repeated perpendicular marks using retained geometry,
without another algorithmic helper. The analytic experiment alone does not satisfy that
public-workflow transfer gate. The complete source-scale workload remains a bounded core
performance check, not a prerequisite to rendering a ten-million-segment image.
