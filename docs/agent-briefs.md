real target execution and honest support claims remain required. Count scenarios and
capabilities in progress reports, not loop-expanded assertions.

implementation bugs without root reviewing every iteration. Before the next buildout batch,
record a prioritized bounded deliverable list, model ownership and stopping conditions.
Do not invent quota balances, prices or a reliable finish-date estimate.

candidate output, unless the assignment explicitly forbids building. Syntax checks and a
prepared-mode message do not validate archive readers, review bindings or preservation.

Luna can handle documentation and existing build runners. Root reviews the resulting archive
and final support claims, without debugging each intermediate worker revision.

## Review proposal acceptance

Use explicit record-ID batches and return patches under an assigned `.work/reviews/` path;
the integration owner edits the shared ledger. Each rationale must state the actual
computation and its precise merge/defer/reject boundary. Repeating the candidate text plus
“needs a contract” is not adjudication. Names such as boat, tree, noise, box or triangle
must not decide membership. Missing a match in the current batch is not evidence of absence.

Before accepting a merge, verify a retained representative and computational equivalence,
including whether the candidate returns values, emits geometry, changes pixels or bundles
several stages. Record extracted-component scope explicitly. A rejection must identify the
bundled operation being excluded and any divergence from the report's recommendation.
Do not claim its ingredients are already retained unless their ledger IDs support that claim.

Each semantic proposal must include the exact candidate ID, name, signature and relevant
parent-note excerpt, followed by inputs, outputs, state/order/topology, the proposed retained
computation and the disposition of every remaining component. Check adjacent ordinals: a
parent scene description is not evidence about every candidate in that note. Compare both
members of a proposed merge; an unspecified “policy” must not hide different algorithms.
For rejections, distinguish a public-wrapper exclusion from exclusion of its ingredients.

Keep semantic batches small enough to inspect each cited computation. The integration owner
must independently verify identities and decisive passages before applying a proposal; agent
confidence, repetition and a passing structural check are not acceptance evidence. Use
`--contract-cluster <id>` for operation eligibility after architecture/member audits. Related
unresolved records must be reviewed for impact, even if currently assigned to another family.
Record corrections in the ledger history and preserve deferred component work explicitly.

## Bounded implementation handoff

Complete every assigned deliverable before returning a final implementation handoff.
A syntax check or input gate is a progress checkpoint when fixture execution, packaging,
or consumer checks were also assigned. Send progress while continuing; identify a concrete
blocker when work cannot continue. Do not silently shrink an assignment to its first stage.

Before handoff, compare source against ownership, destination types, allocation and error
requirements as well as running fixtures. Frozen wrappers do not make mutable backing arrays
immutable. Count-only comparisons do not establish example geometry parity. A no-op build
check does not establish that archive construction is implemented. Root still reviews the
important decisions and representative outputs; never skip existing tests to make a
prospective successor pass.
